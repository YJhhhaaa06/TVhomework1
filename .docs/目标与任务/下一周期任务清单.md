## 一、周期约定（本周期全部条目通用，开窗前必读）

| 编号  | 约定                 | 内容                                                                                                                                                               |
| --- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | 一任务一窗口一 commit（默认） | 每个任务开独立窗口，期望产出 1 个 commit（可含多文件）。例外（依赖拆多 commit / 小任务合并）须在任务详情标注，cover 主题仍带任务编号                                                                                  |
| G2  | 开窗协议（输入）           | 新窗口顺序读取：① .docs/INDEX.md → ② 需求与痛点.md 相关章节（决策节必读） → ③ 任务清单.md 当前任务 → ④ 常青文档（涉及架构/业务时） → ⑤ 上一个任务 commit                                                           |
| G3  | 收窗协议（输出）           | 完成后：① codex/主会话跑 `python tools\run_tests_report.py all`（AGENTS.md 强制） → ② 勾选任务清单状态 → ③ 涉及架构/业务改动时同步常青文档 → ④ 提交。plan 产物留在窗口内工作树下（.docs/temp/ 或工作树内），**不进 commit** |
| G4  | commit 语义闭环        | 代码改动 + 其对应的常青文档更新 + 任务清单勾选进**同一 commit**；commit message 强制带任务编号（如 `feat(test-01): 测试体系整合基线`）                                                                     |
| G5  | 超范围暂停规则            | 执行中发现需求歧义、或任务实际远超预期 → **停在第一个决策点**，回写任务清单（拆/改），不得硬扛、不得擅自扩大范围                                                                                                     |
| G6  | 评审与返工              | 评审以"任务验收标准 + 测试结果"为准，不凭感觉退稿；返工状态记录在任务清单（如"任务-02：×次返工"）；连续返工 ≥2 次 → 返回周期设计重新评估（任务拆错/目标不清）                                                                         |
| G7  | 决策唯一源              | 需求与痛点.md 第四节为唯一决策源；窗口内发现新决策 → 回写该节并标记"已定/待定"，**不许自行拍板**                                                                                                          |
| G8  | 分支与合并              | 周期内设一个 integration 工作树/分支（从 master 开）；每个任务工作树从 integration **最新 commit** 开，完成后合并回 integration（保留历史、不 squash，一个 commit=一个任务）；周期结束 integration 合入 master           |
| G9  | DDL 备份             | 本周期预计无 DDL；若任何任务出现表结构改动，执行前必须先备份库结构与建表语句到 `.docs/DBbackups/`（沿用 260830 强制要求）                                                                                     |
| G10 | 脚本规范               | 临时一次性脚本放 `temp_script/`，长期复用/自动化脚本放 `tools/`（AGENTS.md 已持久化）                                                                                                     |

## 三、任务详情

### T1 测试体系整合基线

* **背景**：三套体系（.http \~302 例手跑 / pytest \~46 例 / JUnit 92 例）重复覆盖、定位不清，回归置信低。

* **范围**：

  1. 按 D-5 明确三层定位（建议：JUnit=单元基准、pytest=端到端、.http 降级本地调试不纳入考核）；
  2. 去重试点：以"删除作品"三处覆盖（ContentServiceTest/test\_delete\_content/deleteContentTest.http）为试点，确定最终载体并迁移，明确后续去重规则；
  3. 沙盒环境收敛：把 TEST\_AUTOMATION.md 记录的沙盒环境变量（离线仓库、18080 独立 Tomcat、pytest-deps 本地目录）收敛到 `tools/run_tests*.py` 默认值+可覆盖。

* **改动面**：`tools/run_tests*.py`、`src/test/python/*`（定位相关）、`src/test/*.http`（取舍）、`.docs/说明书/TEST_AUTOMATION.md`。

* **验收**：① 三层定位在 TEST\_AUTOMATION.md 明确；② "删除作品"只保留最终载体、另两类作本地调试/移除非必跑；③ `python tools\run_tests_report.py all` 通过（JUnit + pytest）；④ 生成的内容变更均有对应 commit message 带 `test-01`。

### T2 测试数据隔离

* **背景**：pytest\_/smoke\_ 前缀数据污染生产库，需 cleanup\_data.py 事后清理（P2）。

* **范围**：按 D-6 落地隔离方案——独立测试库或种子数据+自动清理；改造 pytest 基建（conftest.py / pytest.ini）与清理流程；若选独立库，处理测试库连接配置与密码安全（不把密码写进被追踪文件）。

* **改动面**：`src/test/python/conftest.py`、`pytest.ini`、`tools/cleanup_data.py`（或替代）、`tools/run_tests*.py`、`src/main/resources/app.properties`（仅测试库连接，视 D-6 而定）。

* **验收**：① 跑完整测试后，生产库 TVDatabase 无 pytest\_/smoke\_ 前缀残留（校验步骤写入收窗协议）；② 测试仍能独立完整跑通；③ 文档同步（说明书/TEST\_AUTOMATION.md）。

### T3 完整性校验统一工具

* **背景**：脏数据排查要跑多个工具，无单一入口（P3）。

* **范围**：新增 `tools/check_integrity.py`，收拢现有检查逻辑——孤儿 content\_media / 孤儿 comment\_like（cleanup\_data 检查项）、孤儿媒体文件（cleanup\_orphan\_media 检查项）、缺失/重复引用；dry-run 默认、报告落盘 `.docs/temp/`；退出码约定（0/安装缺失/连接失败等，参照 cleanup\_orphan\_media 安全设计：连接门禁+重叠校验）。

* **改动面**：`tools/check_integrity.py`（新）、`tools/cleanup_data.py` / `cleanup_orphan_media.py`（改为复用或明确职责边界）、`.docs/说明书/AVAILABLE_TOOLS.md` 或对应说明。

* **验收**：① dry-run 一次可列出三类脏数据清单；② 数据库不可达时未触碰任何数据（安全门禁）；③ 与既有工具职责边界文档化；④ 脚本经 subagent 审查（沿用 260830 审查约定）。

### T4 计数漂移校验与修复

* **背景**：like\_count/comment\_count 由应用层 ±1 维护、无外键、缓存更新在事务外（P4/P5），漂移风险随 260830 功能扩大。

* **范围**：在 T3 框架内扩展（或独立脚本）——校验 `content.like_count`/`comment_count` 与实际点赞/评论记录数一致；修复走显式 `--fix`（统计重算，不改业务逻辑）；输出与 T3 报告统一。

* **改动面**：`tools/check_integrity.py` 扩展、`CountRepairTool` 能力整合、`.docs/常青/BUSINESS_FLOW.md`（问题4 状态备注）。

* **验收**：① 人为制造漂移后可被校验发现；② `--fix` 后计数与记录一致；③ 全量回归通过、无业务行为变更。
