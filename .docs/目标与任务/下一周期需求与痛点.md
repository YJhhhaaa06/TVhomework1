# 下一周期需求与痛点

> 用途：回答"下一周期为什么做这些"——本周期要解决的痛点、候选任务的优先级映射、以及开工前必须拍板的技术决策。
> 状态：**草稿待评审** —— 任务拆分与决策确认后，进入任务清单文档执行。
> 术语约定：**周期（本文档所规划的投入范围）> 任务（一个窗口=一个 commit 的最小执行单元）**。为消除歧义，本项目文档从本周期起不再使用"阶段"一词描述执行顺序；历史文档中的"阶段"仅指 260830 周期内部顺序，已归档。

***

## 一、本周期目标（Why）

more-functions 分支（260830 周期，7 项功能）合并到 master 后，**本周期不做新业务功能**，只做"地基与加固"：

1. **测试体系可靠化**：消除三套测试体系（.http / pytest / JUnit）的重复覆盖与定位混乱，让后续任何改造有可信的回归基线。
2. **脏数据源头治理**：测试数据不再污染生产库（治本），并提供统一的完整性校验手段（治标），为后续"缓存改造"周期铺路。

> 后续周期（不在本周期范围，仅预告）：缓存改造（拆分 ContentCacheManager 650+ 行 god class + 统一缓存接口；Redis 化视决策而定）→ feature package 改造（等代码规模变大或单独练手时再做）。

## 二、痛点清单

| 编号 | 痛点                                 | 来源/证据                                                                                                                 | 影响                    | 优先级       |
| -- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------- | --------- |
| P1 | 三套测试体系重复覆盖、定位不清                    | 单一功能三处覆盖（如删除作品=JUnit+4/pytest+7/.http+6）；.http \~302 例仅手跑、无断言框架；JUnit 92 例、pytest \~46 例各自独立                          | 维护成本高、改动一处要同步三处、回归置信低 | 高         |
| P2 | 测试数据污染生产库                          | pytest/smoke\_ 前缀内容、其关联媒体/评论/点赞残留 TVDatabase，需 cleanup\_data.py 事后清理（AGENTS.md/说明书均有记录）                               | 数据环境不可信、脏数据反复出现       | 高         |
| P3 | 脏数据缺乏统一校验手段                        | 现有工具各自为政：cleanup\_data.py（测试污染/孤儿记录）、cleanup\_orphan\_media.py（孤儿媒体文件）、MediaAuditService（媒体完整性）、CountRepairTool（计数修复） | 排查一次脏数据要跑多个工具、无单一入口   | 中         |
| P4 | 计数漂移隐患（like\_count/comment\_count） | 计数由应用层 `±1` 维护、无 DB 外键；BUSINESS\_FLOW 问题4 已记录"缓存更新在事务外、靠定时刷新兜底"；260830 周期新增删内容/软删/楼中楼扩大了计数维护面                         | 计数不准会扩散到列表/排序/展示，难查   | 中         |
| P5 | 缓存一致性弱点（非本周期改造，但为 P4 关联项）          | BUSINESS\_FLOW 问题4：`LikeService.likeContent` 缓存更新在事务外                                                                 | 与 P4 同源，记录备查          | 低（本周期仅记录） |
| P6 | 优惠券抢购无用户限流                         | BUSINESS\_FLOW 问题5：`CouponService.grabCoupon` 依赖数据库行锁+唯一索引兜底，不超卖但体验差                                                  | 低成本小改进，作为候选顺手项        | 低（默认不做）   |
