## 三、数据模型注意点（重要）

### 3.1 现状：comment.is_deleted 一个字段承载两种语义

DATABASE.md 中 comment 表定义：

```sql
is_deleted TINYINT DEFAULT 0  # 0正常显示，1被删除(可恢复),用于关闭评论区
```

即：**单条评论的"被删除" 与 "整个评论区关闭" 共用同一字段**，两种语义互相干扰，不能满足本次业务需求。

### 3.2 新业务需求拆分的语义

| 语义 | 归属 | 说明 |
|------|------|------|
| 评论软删除 | comment.is_deleted | 表示**单条评论**被删（用户自删/管理员删）；记录保留、用户不可见且**不可恢复**；删除规则见 3.5 楼中楼 |
| 评论区开关 | content 表**新增字段** | 表示作者**整个内容**的评论区开/关；与每条评论的删除状态无关 |

### 3.3 建议的数据模型调整

- `comment.is_deleted`：语义收窄为"单条评论软删除"（0=正常，1=已删，无恢复），不影响评论区开关。
- `comment.parent_id`：语义调整为**一律指向主楼**（楼中楼两层结构，见 3.5）：一级评论 parent_id=NULL，楼内回复 parent_id=主楼 id（存量数据需一次性迁移重挂）。
- `comment` 新增 `reply_to_user_id`（楼中楼 @ 引用，见 3.3/3.5；**2026-08-28 已落地**）：回复楼内回复时记录被回复评论作者 id。
- `content` 表新增评论区开关字段，如 `comment_enabled TINYINT NOT NULL DEFAULT 1 COMMENT '评论区开关: 1-开, 0-关'`（与 is_deleted 区分，名称在实现时定）。
- `ContentCacheDTO` 增加 comment_enabled 字段，随缓存 backfill/刷新一起更新（见 3.4 决策3）。
- 效果：关评论区时不逐条改 comment 的 is_deleted；开评论区时也无需"恢复"评论。

### 3.4 决策结论（2026-08-26 已确认）

1. **评论展示模式**：改用 **B站楼中楼**（见 3.5），删除规则随模式而定，取消"子孙级联隐藏"方案。
2. **删除者区分**：用户自删与管理员删**均不可恢复**，**不区分删除者**（无需 deleted_by 字段，管理员也无恢复入口）。
3. **评论区开关的查询**：开关字段加入 **ContentCacheDTO**，详情页按开关状态决定是否展示评论区入口。

### 3.5 B站楼中楼模式（2026-08-26 定案）

**动因**：树形展示下软删中间节点会导致子孙"浮空"（找不到父）；旧方案"级联隐藏"虽能解决但会连带删掉整段对话。楼中楼让每条评论**只依赖主楼**，删除天然不破坏结构。

**结构**：

```
主楼  R1  ← parent_id = NULL（一级）
  ├── 回复 A  ← parent_id = 主楼R1
  ├── 回复 B  ← parent_id = 主楼R1
  └── 回复 C  ← parent_id = 主楼R1（回复的回复也平铺挂主楼）
```

- 数据层仅两层：主楼 + 楼内回复（**回复的回复也挂主楼 id**，新增 `reply_to_user_id` 字段记录被回复的作者，楼中楼展示「回复 @xxx」）。
- 展示层：主楼卡片 + "共 N 条回复"平铺列表。
- **回复入口：主楼与楼内回复均可回复**（2026-08-28 修复：楼内回复增加回复按钮；parentId 传被回复的评论 id，后端自动上溯挂主楼并记录 reply_to_user_id）。

**删除规则**（软删除，均不可恢复）：

| 删除对象 | 规则 | SQL 形态 |
|---------|------|---------|
| 主楼 | **整栋楼软删** | `UPDATE comment SET is_deleted=1 WHERE comment_id=主楼 OR parent_id=主楼` |
| 回复 | **只删自己** | `UPDATE comment SET is_deleted=1 WHERE comment_id=回复` |

**结论**：删除任意回复不影响其它回复展示，"找不到父"从结构上消除；删主楼才动整楼。

**切换改动面**（详见计划阶段一）：
- 存量数据迁移：把现有递归树评论的 parent_id 重挂回主楼（Python 脚本，遵循项目脚本规范）
- 代码：`CommentCacheDTO.children` 移除（或仅挂主楼）、`buildCommentTree` / `insertChildToTree` / `updateCommentLikeCountInTree` 递归逻辑改为两层、`CommentVO` 相应调整
- 前端：detail.js 评论区递归渲染 → 楼中楼（主楼 + 展开/收起回复列表）

## 四、功能间耦合关系（技术参考，供决策顺序）

```
A1 删除内容 ──► B2 删媒体（配合）
          ──► C1 评论软删除（配合，删除内容时把其评论一并软删）
B1 换源     ──► 复用媒体删除/回填逻辑（可独立）
```

- A1 是把"删除"做对的关键一步，其余清理逻辑可复用；
- C1（评论软删除）是 C2（开关评论区）的前置——关闭/隐藏逻辑也要过滤 is_deleted 评论；
- B1（换源）依赖最小，可率先独立完成。
